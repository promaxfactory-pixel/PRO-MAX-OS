# UPDATER.md — Self-Update Endpoint & Feed Format

PRO MAX OS uses the Tauri 2 updater plugin
(`@tauri-apps/plugin-updater` + `tauri-plugin-updater`). This document defines
the update server contract that `releases.promaxos.com` must implement.

## 1. Endpoint layout

Configured in `src-tauri/tauri.conf.json`:

```json
{
  "plugins": {
    "updater": {
      "endpoints": [
        "https://releases.promaxos.com/update/{{target}}/{{bundle_type}}/{{current_version}}"
      ],
      "pubkey": "dW50cnVzdGVk..."
    }
  }
}
```

Placeholders substituted by the plugin at runtime:

| Placeholder | Value on Windows x64 |
|-------------|----------------------|
| `{{target}}` | `windows-x86_64` |
| `{{bundle_type}}` | `nsis` or `msi` — whatever bundle the client was installed from |
| `{{current_version}}` | e.g. `2.6.3` |

Because `{{bundle_type}}` is part of the path, NSIS and MSI installs get
**separate update records** — important since the two installers are distinct
artifacts with distinct versions.

## 2. Response format (per-bundle `updates.json`)

Each request must return a JSON array (single-element). The `signature` is the
verbatim content of the `.sig` file produced during the signed build.

```json
[
  {
    "version": "2.6.3",
    "notes": "See https://github.com/promaxfactory-pixel/PRO-MAX-OS/releases/tag/v2.6.3",
    "pub_date": "2026-08-16T00:00:00Z",
    "platforms": {
      "windows-x86_64": {
        "signature": "<full .sig content>",
        "url": "https://github.com/promaxfactory-pixel/PRO-MAX-OS/releases/download/v2.6.3/PRO%20MAX%20OS_2.6.3_x64-setup.exe"
      }
    }
  }
]
```

Notes:

- URL-encode spaces in asset names: `PRO MAX OS` → `PRO%20MAX%20OS`.
- `signature` must be the exact `.sig` text (a base64 blob followed by a
  `trusted comment:` line). Keep the trailing newline.
- The plugin verifies the signature against the embedded `pubkey` before
  downloading. It does **not** compare the filename in the trusted comment.
- If no update is available, respond `204 No Content` (or omit the record —
  the client then treats the install as up to date).

## 3. Server file layout (suggested)

```
/update/windows/nsis/2.6.2.json
/update/windows/nsis/2.6.3.json
/update/windows/msi/2.6.2.json
/update/windows/msi/2.6.3.json
```

Each `<version>.json` is generated by the release pipeline into
`release/PRO MAX OS <ver>/updates/windows/<bundle_type>/<ver>.json` and copied
to the server as-is. The installer assets themselves are hosted on the GitHub
release (the `url` field above), so the server only needs to serve the JSON
feed files.

## 4. Key rotation

The `pubkey` embedded in `tauri.conf.json` is baked into each client build.
Installed clients only accept signatures verified by the key embedded in *their*
build. Rotating the key therefore breaks in-place updates for older installs
until they update some other way; document any rotation in the changelog and
bump the version with a user-visible change.

## 5. Local verification (without a server)

Verify a release's signature client-side without a network:

```powershell
cargo run --release --example verify_updater_sig -- `
  <installer>.sig <installer> C:\Users\USER\.tauri\promax-os.key.pub
```

Expected output: `SIG_VERIFY_OK`. This uses the exact verification path the
client plugin uses (base64-decode pubkey and signature, decode, `verify`).
